# Cutting a release

A commit to `main` never publishes anything. A release starts when a
`perfr-v*` tag is pushed. That tag starts two workflows:
[`release-rust.yml`](../.github/workflows/release-rust.yml) (the GitHub
Release) and [`python-wheels.yml`](../.github/workflows/python-wheels.yml)
(PyPI).

## Tags

| Tag | Result |
|---|---|
| `perfr-vX.Y.Z` | Stable release, marked **Latest**. perfr.dev serves it and the installers download it. |
| `perfr-vX.Y.Z-suffix` (e.g. `-rc.1`) | Prerelease, not Latest. perfr.dev and the installers ignore it. |

The publish job refuses any other tag. `v1.*` and `nightly-*` are the legacy
C++ line; do not reuse them. Neither workflow creates a tag.

There is no changelog file. The release notes are generated by the publish
job and end with the file sizes from that run.

## Manual steps

1. **Once, before the first release that needs them:**
   - Symbol store: add the repository secrets `PERFR_SYMBOL_STORE_BUCKET`,
     `PERFR_SYMBOL_STORE_ENDPOINT` (for R2,
     `https://<account>.r2.cloudflarestorage.com`),
     `PERFR_SYMBOL_STORE_ACCESS_KEY_ID` and
     `PERFR_SYMBOL_STORE_SECRET_ACCESS_KEY`, and optionally
     `PERFR_SYMBOL_STORE_REGION` (default `auto`) and
     `PERFR_SYMBOL_STORE_PREFIX`. Without them the upload step is skipped
     with a message; the symstore archives are still on the release.
   - PyPI: configure Trusted Publishing for `perfr-api` and `perfr`, using
     the `pypi` environment of this repository. Without it the wheel
     publish job fails; the GitHub Release is unaffected.
2. **Bump the wheel version** if the Python packages ship. It must match in
   `crates/perfr-api/Cargo.toml`, both `pyproject.toml` files, the
   `perfr-api==` pin in the `perfr` package and both `__version__` values
   (see [`tools/release/README.md`](../tools/release/README.md));
   `build_wheels.sh` refuses to run when they drift. The Cargo version of
   `crates/perfr` is independent of the tag.
3. **Tag and push** the commit to ship:

   ```sh
   git tag perfr-v0.1.0
   git push origin perfr-v0.1.0
   ```

4. **Check** that the `linux`, `macos`, `windows` and `publish` jobs are
   green, then open `https://github.com/perfr/perfr/releases/tag/<tag>`.
   perfr.dev serves a stable release a minute or two later.

A manual run (Actions, then release-rust, then Run workflow) with an empty
**tag** builds every artifact and publishes nothing. With **tag** set to an
existing `perfr-v*` tag, it creates the release for that tag. A manual run of
python-wheels builds wheels and never publishes.

## release-rust.yml

Three build jobs run in parallel, then `publish`.

| Job | Runner | Builds | Installer archive |
|---|---|---|---|
| `linux` | `ubuntu-22.04` | static musl `perfr` (viewer embedded); glibc `perfr-hook`, `libperfr.so` (`--features native`), `perfr-gpu` | `perfr-linux-x86_64.tar.gz` |
| `macos` | `macos-15` | `tools/build/build-service-macos.sh --universal`: universal `perfr`, `perfr-hook`, `libperfr.dylib`. Ad-hoc signed, not notarized. No GPU helper. | `perfr-macos-universal.tar.gz` |
| `windows` | `windows-2022` | `tools/build/build-service-windows.ps1`: static-CRT `perfr.exe`, `perfr-hook.exe`, `libperfr.dll`. Not code-signed. No GPU helper. | `perfr-windows-x86_64.zip` |

Each archive has a top-level `perfr/` directory and `licenses/` (the Frida
notices). `perfr.h` is `include/perfr.h` in that directory, not beside the
binary. Frida is linked statically: Core into
`perfr-hook`, Gum into `libperfr`, from the devkits that
`tools/frida/devkits.sh` downloads. Linux arm64 is not released.

**Debug symbols.** Release builds compile with full debug info (dependencies
excluded), and `tools/release/split_debug.py` moves it out of the shipped
binaries:

| Platform | Split | Left in the binary |
|---|---|---|
| Linux | `objcopy --only-keep-debug`, `--strip-debug`, `--add-gnu-debuglink` | symbol table, GNU build-id (`-Wl,--build-id=sha1`) |
| macOS | `dsymutil`, `strip -S`, ad-hoc `codesign` | Mach-O UUID |
| Windows | the PDB cargo writes, left out of the zip | RSDS pointer |

Each job also packs `perfr-<tag>-<target>-debug.tar.gz` and
`perfr-<tag>-<target>-symstore.tar.gz`, plus a `.sha256` for every archive
and `sizes-<target>.txt`. The symstore layout is
`buildid/<id>/debuginfo` (debuginfod) on Linux,
`<name>/<GUIDAGE>/<name>` (SymSrv) on Windows and `dsym/<uuid>/` on macOS.

The disassembly view finds detached Linux debug info through
`.gnu_debuglink`, `/usr/lib/debug/.build-id`, or
`PERFR_SYMBOL_PATH/buildid/<id>/debuginfo`.
`python3 tools/release/test_split_debug.py` tests the splitter.

**publish** (`contents: write`):

1. Downloads the artifacts from the three build jobs and writes `SHA256SUMS`.
2. Unpacks the symstore archives and syncs them to the bucket with
   `tools/release/upload-symbols.sh`, or skips with a message if the secrets
   are unset. You can run the same script later by hand.
3. Validates the tag, writes the release notes and runs
   `gh release create --verify-tag` with every file, as `--latest` for a
   stable tag or `--prerelease` for a suffixed one.

## `perfr update`

`perfr update` downloads the latest stable `perfr-v*` release, or the tag
given with `--version`, verifies the `.sha256` sidecar or `SHA256SUMS`, and
replaces this install. It uses the layout in the next section, deletes the
retired files below, and prints each path it removes. Linux, macOS, and
Windows are the same command. A running `perfr` keeps the previous image
until it is started again.

```
updated perfr 0.1.1 -> 0.1.2 in ~/.local/bin
restart any running perfr to use the new version
```

On Windows the directory is the install folder (`perfr.exe`'s directory),
not `bin`. A current install prints `perfr 0.1.2 is up to date` and does not
download the archive. A build newer than the release is left in place:
`perfr 0.1.2 is newer than the latest release 0.1.1`.

`perfr update --check` does not download the archive. It prints three lines
and exits:

```
current: 0.1.1
latest: 0.1.2
status: update available
```

`status` is `up to date`, `update available`, or `newer than latest`. When a
package manager owns the binary, two more lines name it and the command to
run (`installed by: homebrew`, `update with: brew upgrade perfr`). `--version`
compares against that tag and still prints it as `latest`.

| Exit | Meaning |
|---|---|
| 0 | Up to date, newer than the release, or (without `--check`) the install was replaced |
| 1 | `--check` only: a newer release is available |
| 2 | Download, checksum, or install failure. A cargo, Homebrew, or pip install is not overwritten, and that refusal is also 2 |

`--yes` is accepted and ignored, so older scripts that passed it still update.
`--check` never replaces the install, with or without `--yes`.

## Install layout

The installers and `perfr update` do not leave `perfr.h` beside the binary.
The header still loads `libperfr` from beside `perfr` on `PATH`.

- Linux and macOS: binaries go in `~/.local/bin` (`PERFR_INSTALL_DIR`
  overrides that directory). The header goes in the sibling include
  directory, `~/.local/include/perfr.h` by default. `install.sh` creates
  the directory and tells the user to compile with `-I~/.local/include`,
  or `-I` plus the overridden path.
- Windows: the zip already has `include\perfr.h`. `install.ps1` leaves it
  at `<install dir>\include\perfr.h` (default
  `%LOCALAPPDATA%\Programs\perfr\include\perfr.h`) and prints `-I` for
  that directory.

`perfr update` writes the header to the same place. An older archive that
still has `perfr/perfr.h` at the top is installed there. When both
`perfr/perfr.h` and `perfr/include/perfr.h` are present, the `include/`
copy is the one installed.

## Retired files

`install.sh`, `install.ps1`, and `perfr update` delete files a previous
install left in the install directory, and print each path they remove:

- `perfr-frida-helper`, `libperfr_frida_agent.so`,
  `libperfr_frida_agent.dylib`, `libperfr_api.so`, `libperfr_api.dylib`,
  `perfr-gpu-helper`
- `perfr_frida_agent.dll`, `perfr_api.dll`, `perfr-frida-helper.exe`,
  `perfr-gpu-helper.exe`, and the `.pdb` / `.lib` siblings those builds
  shipped (`perfr-frida-helper.pdb`, `perfr-frida-helper.lib`,
  `perfr-gpu-helper.pdb`, `perfr-gpu-helper.lib`, `perfr_frida_agent.pdb`,
  `perfr_frida_agent.lib`, `perfr_frida_agent.dll.lib`, `perfr_api.pdb`,
  `perfr_api.dll.lib`)
- a `perfr.h` left next to the binary, now that the header lives under
  `include`

`perfr_api.lib` and `libperfr_api.a` stay; they are the static libraries.
The list is `RETIRED_INSTALL_FILES` in `crates/perfr/src/update.rs`, and
the two installers keep the same names.

## python-wheels.yml

On a `perfr-v*` tag it builds wheels with `tools/release/build_wheels.sh` for
`linux-x86_64`, `linux-aarch64`, `macos-arm64`, `macos-x86_64` and
`windows-x86_64`. Its `publish` job (environment `pypi`) then uploads them
with Trusted Publishing. `perfr-api` carries the API-only `libperfr`. `perfr`
carries the `perfr` binary, the full `libperfr`, `perfr-hook` and `perfr.h`.

## perfr.dev downloads

The repository is private, so GitHub does not serve release assets
anonymously. Every minute, `deploy/fetch_release.py` in perfr-web asks GitHub
for the latest stable release, using a read-only token kept on the server.
When there is a new one, it downloads the assets, checks them against
`SHA256SUMS` and rebuilds the site with them under
`https://perfr.dev/download/`.

`https://perfr.dev/install.sh` and `install.ps1`, copied there by perfr-web's
`build_site.py`, download from that path. `PERFR_INSTALL_BASE` overrides it,
and `PERFR_VERSION` picks a GitHub tag, which works only once the repository
is public. Until a stable tag exists the installers exit with a message.
