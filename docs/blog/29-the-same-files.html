The Same Files

The Perfetto UI and the perfr viewer, on Perfetto's own example traces, in one headless Chrome. The table includes the places perfr is slower.

15 November 2026, 08:10–08:53 UTC. perfr 0.1.4 (fd8ba5aaf61c), the build https://perfr.dev/viewer/ reported in window.__perfr_sel.build on every run. Perfetto UI stable v59.1-79997ada9 (79997ada96b2587556cfc3851434407fbed289b1). Chrome 157.0.8103.50, headless, SwiftShader. Medians of five runs are in docs/blog/metrics/perfetto-compare.json. The script is tools/bench/perfetto-compare/.

This is a comparison of two pages that open a trace in the browser. One is the Perfetto UI. The other is the viewer perfr.dev embeds, which on this day was the perfr 0.1.4 release, not a dev build. Both were given the same bytes, from disk, after the page shell was already up. The clock does not include downloading the viewer.

perfr does read Perfetto protobuf. A .pftrace is a stream of length-delimited TracePackets, walked in crates/perfr-live-chrome without protoc, and the same ingestor the Chrome JSON path uses. The Android example below is 58 MB of that format and came out as 643,775 events, with the scheduler and SurfaceFlinger on the timeline. The gap is not “protobuf versus JSON”. It is everything the walker does not map, and the places the picture is slower once it is up.

How the numbers were taken

One machine: Linux 6.12, four Xeon cores, 16 GB. Chrome was started with --headless=new --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist --window-size=1600,1000. SwiftShader is software GL. perfr's readout said WebGL, which is the viewer's default. ?webgpu was not set. There is no display vsync. A frame time here is the gap between requestAnimationFrame callbacks while the script is also injecting the next input. It is not a 60 Hz panel, and a number near 60 fps is this Chrome's idle rate, not a measured redraw of a dense timeline.

Fetching http://127.0.0.1 from https://ui.perfetto.dev is refused. Chrome's local-network check blocks it before the request is sent, even with Access-Control-Allow-Private-Network. The files were downloaded once and opened through each page's file control: perfr's Open pill, whose rectangle is window.__perfr_ui, and Perfetto's input.trace_file. The clock starts when the file is handed over, and stops when that viewer's own “the trace is up” signal fires. For perfr that signal is the status line leaving Loading name N / N (published as symbols-status: in __perfr_ui) with a non-zero event count and a content span, stable across two 50 ms polls. Event count alone is not enough: on the 58 MB file it sat still for a frame at 485 events while the status line still said 18.9 MB of 58.2. For Perfetto the signal is the sidebar switching to CURRENT TRACE with an overview canvas, stable across two polls. Duration: is painted into a canvas and is not in the DOM text. The 50 ms poll is the resolution of both clocks.

A second clock, interaction, is the open time plus the wait until a held W actually moves the view. perfr publishes the window in __perfr_sel.view. Perfetto does not, so the check hashes a PNG clip of the timeline, which adds one screenshot to Perfetto's interaction time and not to perfr's. Puppeteer's keyboard.press is delivered, and a listener on the page sees the keydown, and the perfr build does not zoom. A CDP rawKeyDown held for 220 ms does, because the viewer samples keys once a frame and a frame on these traces is often longer than a tap. Both pages were driven that way. The sequence after the first zoom is ten W, ten S, twelve A, twelve D, each held 220 ms, then eight Ctrl+wheel steps in and eight out, then a 240 px pan. perfr pans on a left drag. Perfetto's left drag is an area selection and its pan is Shift+left. Same distance, the gesture each UI documents.

The two pages do not open on the same framing. perfr fits the timed events and, on the Android example, draws the scheduler and SurfaceFlinger across the window. Perfetto opens on the whole trace, with the overview strip coloured and the track area zoomed out far enough that individual slices are easy to miss, and on this file it also opened an Android logs panel of 1,851 lines. The frame rates below start from those defaults and then zoom. They are not a comparison of the same picture.

Memory is the sum of ps RSS for the Chrome process and its children, sampled every 100 ms. Before the file is opened that sum is already about 1.18 GB for perfr and 1.22 GB for Perfetto: the browser, the GPU process, and the Wasm heap. performance.memory does not include the shared Wasm memory and is not used below. The peak is the high point from the open through the gesture. The trace's own cost is the difference, and the table gives both.

Five runs, a fresh browser each time, one profile so the second navigation is not a cold download of the viewer. The summary is the median of the runs that succeeded. Perfetto's frame rate on the Android files is bimodal: most runs are a few frames a second, and one or two sit near 60, which is the idle rate. The median falls on the slow cluster. The range is in the notes under the table. perfr's frame rate on those files does not do that. It sits in a band of a few tenths of a frame per second across the five runs.

On the three Android traces both viewers are at a few frames a second while the keys are held. perfr's median is the higher one (4.3, 4.7, 5.3 against 3.9, 2.0, 2.8), and Perfetto's is the less stable one: the five frame rates on the 15 s file were 1.8 to 57.4, and on the 30 s file 2.2 to 59.7. A 57 fps run is a run that did not keep the renderer busy. I would not rank the two on that median alone.

On the Chrome traces perfr is slower, and the gap is not subtle. The Wikipedia example is 4.0 fps against 14, with p50 frame times of 233 ms against 83 ms, and the five perfr runs sit between 3.4 and 4.3. The scroll trace is 7.3 against 27. The legacy JSON example is 14.9 against 59.9, and 60 is the idle rate, so Perfetto was not struggling with 27,622 events. The rendering trace is the close one, 8.4 against 9.3. The histogram gzip goes the other way, 15.1 against 11.3, with one Perfetto run at 34.9 and the other four near 11.

The small files say something the large ones hide. A 16-event async trace and a 3-event counter trace still cost perfr about 18 fps, p50 50 ms. That is the floor of this viewer in headless SwiftShader, not the cost of the trace. Perfetto on the same files sits on the 60 fps idle rate. Any comparison that only used a toy JSON would have reported that floor and called it the trace.

Memory, read as the peak minus the ~1.2 GB the browser already held: perfr adds 72–185 MB on every file except the Wikipedia trace, where it adds 2,372 MB and the peak is 3,551 MB. Perfetto adds 592–759 MB on the Android files and 556 MB on Wikipedia, and its peak there is 1,772 MB. The one Chrome trace the UI offers as the example is the one place perfr's heap runs away. 298,037 events is not, by itself, an explanation: the 15 s Android file produced 904,751 events and added 178 MB.

What perfr is missing

Every gap above, in one place, against main as it is. Partial means the row is not the Perfetto feature.

  • Systrace text. A standalone .atr / TRACE: file is rejected. Five runs, zero opens, the message chrome trace: expected [ or {, got d. Embedded systemTraceEvents and ftrace print inside a protobuf are a different path and do load.
  • SQL, Trace Processor, and the metrics page. No query box, no PerfettoSQL, no standard-library metrics.
  • Pinning tracks, an overview minimap, and opening several traces at once.
  • Area-selection aggregation of slices. Sample ranges and a scope marquee exist. The aggregation tables do not.
  • Heap profiles, java heaps, and Chrome memory dumps. The flame graph is the sampling report's flame only.
  • GPU queues, cpu frequency, process_stats, sys_stats, memory snapshots, and ETW packets. Counted in skipped_packets and dropped. The module comment in perfetto.rs is the list.
  • Android logs, binder, frame timelines, and battery. The Perfetto page showed the logs. perfr did not.
  • Callstacks attached to track events, and per-slice thread time. Sampled perf_sample stacks are drawn. callstack_iid and extra_counter_values are not.
  • Flows, incompletely. First id only, and not on async lanes.
  • Argument detail. A hover string, 512 characters, 100,000 entries, then later strings are dropped.
  • Search. Scope names and track names. Not arguments, not SQL, not the track finder.
  • Recording a Perfetto or Android trace from the page.
  • Sharing an imported trace, or a permalink to one. The viewer refuses, in those words.
  • Converting the trace, or handing it back as JSON or systrace.
  • Plugins, the command palette, data explorer, and memscope.

None of that is a claim about a future patch. It is what main and perfr 0.1.4 did with these files on this day.

The short version. perfr 0.1.4 opens Perfetto protobuf, Chrome JSON, and gzip of either, and on the Android example it draws scheduling and SurfaceFlinger. It does not open systrace text. Against the Perfetto UI in headless Chrome with SwiftShader, perfr was faster to open the smaller Chrome traces and slower to open the two big Android traces and the Wikipedia example. Navigation on that Wikipedia trace was 4.0 fps against 14.0, and the Chrome process peaked at 3,551 MB against 1,772 MB. On a 16-event trace perfr still only reached 18 fps, which is the viewer's floor in this setup, while Perfetto sat at the idle 60. The frame rates are not a desktop measurement. SQL, metrics, pinning, heap profiles, Android logs, sharing an imported trace, and a systrace file are not in the viewer.
