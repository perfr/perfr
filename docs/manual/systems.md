# Systems

Where the thread ran, and what the profiler itself is doing. The scheduler is on the [home page](../index.html#systems). The service’s own lanes are on the [features page](../features.html#service).

## Scheduler and thread state

**CSW** draws the scheduler: one lane per core the capture saw, under a track you can fold. `?collapse=scheduler` starts it folded. Hover a slice for which thread was on that core.

Each lane shows the core's top frequency when the capture recorded one, including when every core of the machine has the same one. Where a base frequency was recorded and it is not the same number, the lane shows both (`3.2–4.6`). The capture does not record a frequency trace: the one reading of the current frequency taken at its start (`scaling_cur_freq` on Linux) is in the lane's tooltip, in words, and is not drawn on the lane. A chip is added only where the cores are not alike: `P` or `E` on a machine with performance and efficiency cores (Intel's hybrid parts, big.LITTLE), or the size of the level 3 cache where some cores have a larger one (the X3D Ryzens, `96M` beside `32M`). The stronger kind is in the accent colour, and where the top frequencies differ the highest is in the text colour and the others are muted.

Where the capture recorded SMT pairing, the logical threads of one physical core are labelled `C0  T0` and `C0  T1`: the core, then the thread of it, each in a column of its own so the threads line up. A core with no sibling on that machine is just `C8`. The cores are counted from 0 in the order of their first CPU, so a part of 24 cores is `C0` to `C23`; the system's own core id, which is not a count (a 13900K's are 0, 4, 8 up to 28 and then 32 to 47), is in the lane's tooltip where it differs. Where the lanes of a core's threads are next to each other, a bracket at the left edge of the rail joins them, one bracket per physical core; where the system numbers the siblings apart (Linux on most AMD parts: CPU 0 and CPU 16), there is no bracket and the labels say the pairing. Where it recorded more than one NUMA node, the lanes are tinted by node, with a line and a small `N0` where the node changes. The tint is the capture's node map.

Hover a lane for the rest of what that capture recorded, as a table: the CPU's number and kind, the physical core and which thread of it, the socket, NUMA node, die and cluster; each cache with its size, associativity and which CPUs share it; the min, base and max frequency and the one reading at the start; the power mode, with the cpufreq policy of that CPU and no other; and the machine's model, microcode, cache line, nodes per socket and the ISA flags the capture kept (a selection, and the row says so). The level 3 size is in that table. It is on the lane only when it is the chip that tells the cores apart. Click the lane to copy the table as text, or right-click it for **Copy core info**; the tooltip says when it has been copied. A slice on the lane says the core in one line, with the lane's name (`Core: 17 (C9, Efficiency core, up to 4.30 GHz, 36 MB L3)`).

The scheduler row, over the timeline, names the power mode and nodes per socket when they were recorded (`powersave · boost on · balanced · NPS2`). Click the row to open a diagram of the sockets, nodes, dies or shared level 3 caches, and the threads of each physical core. Hover the row for the same diagram while the pointer is there. A line under the diagram that came from a model table, rather than from the machine, says so, and so do memory-channel marks when the table supplied a count. Click the triangle at the left of the row to fold the track, as before. Right-click the row for Copy CPU info, Search CPU model, and Product page when the model string and the core and thread counts match an entry of the viewer's own table that has a page. A model that does not match has no product link, and a link written into a capture file is never opened. Copy CPU info says a cpufreq policy once for the CPUs that share it (`cpus 0-15: intel_pstate powersave, EPP performance, scaling 0.8–5.5 GHz`).

On Linux the service reads this from sysfs and procfs at the start of the capture, in one walk that the lane marks come from too: topology, cache/index*, cpufreq, the hybrid PMUs or cpu_capacity, NUMA nodes with their memory and distances, and platform_profile. Only the CPUs that are online are listed: one taken offline, or the second thread of each core under `nosmt`, is not a thread of the machine as it ran. Physical cores are counted from the kernel's sibling lists. `powerprofilesctl get` is asked on a thread of its own once the capture is running, and given two seconds: when that program is installed and prints `power-saver`, `balanced` or `performance`, the profile joins the capture a moment after its start, and a capture never waits on it. Nodes per socket is the node count divided by the socket count when that divides evenly, and the summary says it was derived. The hostname is included, as the capture's system record already includes it.

On Windows the topology is what `GetLogicalProcessorInformationEx` reports: kind, caches, NUMA, packages, dies and SMT. There is no per-core frequency in that buffer. The power plan is the active scheme when powrprof answers, the overlay when `PowerGetActualOverlayScheme` is exported, and the processor boost mode is the AC index of that setting. Per-node memory is not read. That path has not been run on a Windows machine. On macOS the brand, counts, cache sizes and perf levels are sysctl, and low power, high power and AC or battery are `pmset`, asked the way `powerprofilesctl` is. macOS has no scheduler track. That path has not been run on a Mac. A capture written straight to a file on either system carries the machine as a served one does.

With `--connect`, each machine says its own cores and topology and the hub keeps them side by side: a remote's are drawn on the lanes the hub gave that machine, and the diagram has a block per machine.

The cores and the topology travel with the capture. A capture recorded by perfr 0.1.6 has the lane marks and no topology frame, so it has no NUMA tint, no SMT labels, no diagram and no power line; where its cores differ it still shows the chip and the top frequency, and where they do not it now shows the top frequency if one was recorded. A capture from perfr 0.1.5 or older, a Chrome or Perfetto trace, and a machine that tells nothing have no marks. The flags kept are a short list (AVX2, AVX-512 and the like), not every flag the kernel printed.

**States** draws a strip of thread states on each thread. The names the tooltip uses are Running (on a CPU), Runnable (ready, waiting for a CPU), Sleeping (interruptible), Uninterruptible sleep, Stopped, Traced, Dead, Zombie, Parked and Idle.

With no thread focused, the scheduler shows the slices of the capture's target in colour and the rest of the machine's in grey. A capture with no target has them all in colour. A saved or shared capture names its target, so it opens with the same slices in colour as when it was captured; a `.perfr.stream` saved by perfr 0.1.5 or older names none, and opens with them all in colour.

Click a thread header to focus it. Click again to release. The scheduler keeps that thread’s slices in colour and greys the others, and a chip above the timeline names it. Clicking one of that thread’s scopes does the same. A click on a scheduler slice, a state bar, or a sample tick does not move the focus. Escape, a click on empty canvas, or the chip’s × clears it.

System-wide scheduling needs `perf_event_paranoid` at 0 or below, or root / `CAP_PERFMON` / `CAP_SYS_ADMIN`. If the lanes stay empty, [Troubleshooting](troubleshooting.html) has the check.

## The service, profiling itself

`perfr` instruments its own capture loop. The value lanes it emits include `service cpu %`, `service rss MiB` and `events per pass`, plus ring fill (`perf switch rings fill %`, `scope rings fill %`, `viewer ring fill %`) and `scope records lost`. A vertical cursor reads them across the capture. The service’s own scopes (`capture pass`, `read samples`, `unwind`, and the rest) sit on its tracks with everything else.

## The viewer’s Self pane

More → “Self   F2”, or the **F2** key, opens a pane with the viewer’s own frame times. **F3** toggles Benchmark, which asks the service for fake scopes at a rate you set. Both are about the tools, not the target. R, I, F2 and F3 do nothing while that Self pane is the one taking keys.
